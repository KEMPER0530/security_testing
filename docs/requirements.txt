あなたは、Webセキュリティ、Python、React、クリーンアーキテクチャ、

────────────────────
1. プロダクト・診断・評価要件
────────────────────

【対象と利用範囲】

利用者本人が所有するサイト、または明示的な診断許可を得たサイトを対象にします。
サイト登録、所有確認、重要度設定、診断、結果確認、再診断を提供してください。

初期版は公開Webサイトの低負荷な診断に限定します。
ログイン後のページ、攻撃を伴う検証、ポートスキャン、
総当たり、認証回避、DoS、データ更新は対象外です。

対象ホスト、許可されたスキーム・ポート・パス範囲、
確認方法、確認日時、有効期限を管理してください。
所有確認はDNS TXTレコードまたは指定ファイルで行います。

所有確認は診断範囲の登録と組み合わせて扱い、
関連サブドメインやリダイレクト先を自動的に許可しないでください。
実行直前にも許可状態と確認期限を検証してください。

【MVPの診断内容】

次を実際の通信結果に基づいて診断してください。

・HTTPSへのリダイレクト、TLS証明書の期限・ホスト名・信頼性
・セキュリティヘッダー、CSP、HSTSの設定
・CookieのSecure、HttpOnly、SameSite属性
・取得したHTMLから確認できるMixed Content
・レスポンス内の不要なバージョン情報などの情報露出

初期版はHTMLの静的解析とし、JavaScript実行後のDOM、
認証後の挙動、内部構成までは確認できないことを表示してください。

ヘッダー不足だけで悪用可能な脆弱性と断定しないでください。
CSPは存在の有無だけでなく、値と適用文脈を評価してください。
TLS証明書の問題で通常の取得に失敗した場合も、
証明書検証を無効化して診断を続行しないでください。

各チェックには、ルールID、ルールバージョン、対象、
判定、確認事実、秘匿化した証拠、影響、確度、
修正例、参考資料、確認日時を持たせてください。

判定は「問題を検出」「問題を検出せず」「確認不能」
「未実施」「対象外」を区別してください。
確認不能・未実施を、問題なしとして集計しないでください。

【システム重要度・データ機密性による3段階】

この3段階はサービス独自の分類です。
国際規格への準拠や認証取得を意味する表示は禁止します。

レベル1：標準
公開情報を中心に扱い、停止・改ざん・漏えいによる影響が限定的なサイト。

レベル2：重要
個人情報、非公開の業務情報、会員機能などを扱い、
停止・改ざん・漏えいが業務や利用者に大きく影響するサイト。

レベル3：最重要
特に機密性の高い情報、決済・金融・医療等の重要処理、
または社会・事業継続への重大な影響があるサイト。

業種名だけで機械的に決定しないでください。
扱うデータ、漏えい時の影響、改ざん時の影響、
停止時の影響、利用範囲、外部公開状況を質問票で収集します。

データの実物や個人情報を質問票に入力させず、
データの分類と影響だけを収集してください。

判定ルールを文章と決定表で定義し、
いずれかの重大条件を満たす場合に、
他の低い項目との平均でレベルを下げないでください。

重要情報が未回答なら「分類未完了」と表示します。
推奨レベル、確定レベル、判定理由、回答、
ルールバージョン、変更履歴を保存してください。
利用者が変更する場合は理由を記録してください。

このレベルは必要な対策の水準を表し、
診断で発見された脆弱性の深刻度や、
対象サイトが現在安全であることを表す数値とは区別します。

上位レベルでも攻撃的な診断を自動的に有効化しないでください。
上位レベルで必要となる認証・認可、業務ロジック、
内部構成等の評価をMVPで実施できない場合、
「追加の専門診断が必要」として不足範囲を表示してください。

【CVSSによる脆弱性評価】

CVSS v4.0を第一候補とし、FIRSTの公式仕様に従ってください。

深刻度は次のとおり表示します。
なし：0.0
低：0.1～3.9
中：4.0～6.9
高：7.0～8.9
緊急：9.0～10.0

CVSSは個別の脆弱性に付与し、
サイト全体の合格点や安全保証として使用しないでください。

採点に必要な事実が不足する場合、
無理に数値を作らず「未評価」と理由を表示してください。
設定改善の推奨事項には、CVSSを付与しない場合があります。
未評価と0.0を区別してください。

CVSSのバージョン、ベクトル文字列、スコア種別、
各メトリクスの根拠、評価元、評価者または算定方法、
評価日時、計算実装のバージョンを保存してください。

基本評価と、環境を考慮した評価を区別してください。
機密性・完全性・可用性の要求は別々に確認し、
3段階のシステム重要度から無条件で全項目をHighにしないでください。

環境評価を行う場合は、その入力値・仮定・根拠を表示してください。
外部由来のCVSS v3.1等を扱う場合は版を明示し、
v4.0に黙って換算しないでください。

計算は仕様への適合を検証できる実装を使用し、
公式のベクトルと期待値で検証してください。
境界値の深刻度分類と、ベクトル・スコアの整合性もテストします。

【対応優先度・結果画面】

システム重要度、CVSS、公開状況、判定の確度を踏まえた
サービス独自の対応優先度を別項目として表示してください。

優先度のルールは決定表で公開し、バージョン管理してください。
CVSSそのものを独自の係数で変更しないでください。
未評価の所見も確認待ちとして扱い、自動的に最低優先度にしません。

ダッシュボードでは、システム重要度、
検出した脆弱性のCVSS深刻度別件数、
設定改善事項、未評価件数、診断カバレッジ、
未実施項目、対応優先度を区別して表示してください。

根拠のない総合安全スコアや「完全に安全」という表示は禁止します。
再診断では同一ルール・対象との対応関係を保持し、
解消、継続、新規、未確認を区別してください。
ルール変更がある場合は単純比較できないことを示してください。

【採用技術】

FE：
React、TypeScript、Vite、React Router、
TanStack Query、React Hook Form、Zod。
日本語UIとし、キーボード操作に対応してください。
状態は色だけで伝えず、文字とアイコンを併用してください。

BE：
Python、FastAPI、Pydantic、Mangum、boto3。
API用Lambdaと診断ワーカー用Lambdaを分離してください。
外部HTTP通信、DNS、TLS検査のライブラリは、
SSRF対策と接続先固定が実現できるかを確認して選定します。

IaC：
AWS CDKをPythonで実装してください。
CDK CLI等に必要なNode.js環境も開発要件に含めます。

開発管理：
JavaScript側はpnpm workspace、Python側はuv workspace。
ルートのMakefile等で両者の操作をまとめてください。
Pythonのタスクを無理にJavaScriptパッケージへ変換しません。

品質管理：
FEはESLint、Prettier、TypeScript、Vitest、
React Testing Library、Playwright。
BEはRuff、mypy、pytest。
依存方向の検証にはimport-linter等を使用します。

実装開始時にサポート中の互換バージョンを公式資料で確認し、
ランタイム、ツール、コンテナを固定してください。
pnpm-lock.yamlとuv.lockを管理し、latest指定に依存しません。

【BEのクリーンアーキテクチャ】

Domain：
対象、許可範囲、診断ジョブ、所見、重要度分類、
CVSS評価、優先度ルールなどの業務概念を扱います。
Python標準ライブラリを基本とし、
FastAPI、Pydantic、boto3、DB、HTTPクライアントに依存しません。

Application：
対象登録、所有確認、診断受付、診断実行、
重要度分類、結果取得、再診断、キャンセル等を実装します。
Domainと、この層で定義するPortに依存してください。

Port：
Repository、JobPublisher、ReportStorage、
SafeWebFetcher、OwnershipVerifier、Clock、
IdGenerator、CvssCalculator等の抽象を、
実際に必要な境界に設けてください。
業務上の抽象をインフラ実装側へ置かないでください。

Adapters：
FastAPIルートとSQSハンドラを入口として扱い、
DynamoDB、S3、SQS、DNS、HTTP/TLS等の実装を出口として扱います。
PydanticのAPI DTOとDomainモデルを分離し、
HTTPステータスやAWS例外を業務層へ持ち込まないでください。

Bootstrap：
環境設定の読み込みと依存の組み立てを担当します。
具象クラスの選択をここに集約してください。

依存方向は外側から内側へ限定します。
DomainからApplicationへの依存、
Domain・ApplicationからAdaptersへの依存を禁止します。

診断ルールの判定処理と実際の通信処理を分けてください。
取得した観測データから判定するルールは、
AWSやネットワークなしでテストできるようにします。

不要な基底クラスや、単なる転送だけの層を増やさず、
境界の目的が説明できる構成にしてください。

【FEの依存方向】

ReactコンポーネントとルーティングはPresentation、
APIクライアントはInfrastructureまたはAdapterに配置します。

業務上の表示判断・分類処理は可能な範囲でReactから分離し、
Domain・ApplicationからReactや生成APIクライアントへの
依存を禁止してください。

React HooksやTanStack Queryは外側の層で使用します。
ローカルUI状態まで過剰にユースケース化しないでください。
権限判定と重要度・優先度の確定はBEを正とします。

【FEとBEの契約】

FastAPIのAPIスキーマからOpenAPIを再現可能な方法で出力し、
TypeScriptの型とAPIクライアントを生成してください。
OpenAPI出力時に実AWSへの接続を必要としない構成にします。

生成コードは手編集せず、
API仕様と生成物の差分をCIで検知してください。
PythonモデルをTypeScriptへ手動コピーしないでください。

日時、列挙値、null、未評価、ページネーション、
エラー形式、APIバージョンの方針を統一します。

3. AWS構成・バックエンドの実装仕様
────────────────────

【AWS構成】

FE配信：非公開S3 + CloudFront + Origin Access Control
認証：Cognito
API：API Gateway HTTP API + FastAPI/MangumのLambda
診断キュー：SQS + DLQ
診断実行：Pythonの診断ワーカーLambda
データ：DynamoDB
レポート：非公開S3
運用監視：CloudWatch
復旧処理：必要なLambdaとEventBridgeスケジュール
Outbox配送：DynamoDB Streamsと配送用Lambdaを基本案とする

FEから診断用LambdaやDBを直接操作させないでください。
API、ワーカー、配送、復旧処理の権限を分けてください。

通常の診断処理はLambdaの実行時間内に収まる上限とします。
長時間・高負荷・ブラウザ実行が必要となった場合の
Step FunctionsやFargateへの拡張条件は設計書に記載します。
MVPで不要なサービスは追加しません。

【認証・認可】

CognitoのAuthorization Code + PKCEを基本とし、
SPAにクライアントシークレットを埋め込まないでください。

API Gatewayとアプリの責務を明確にし、
未検証のJWTや、クライアント指定のユーザーIDを信用しません。
署名、issuer、対象クライアント、期限、トークン種別、
必要なscopeの検証方法を定義してください。

ユーザー識別子は検証済み認証情報から取得します。
対象、ジョブ、所見、レポートの全経路で認可してください。
他ユーザーのIDを指定しても参照・変更できないことを検証します。

【API】

以下の機能をREST APIとして実装し、OpenAPIで定義してください。

対象管理：
対象の登録・一覧・詳細・削除、所有確認チャレンジの発行と検証。

評価設定：
重要度質問票の登録・取得、分類結果・理由・履歴の取得。

診断管理：
診断受付、一覧、状態取得、キャンセル、再診断。

結果取得：
所見一覧・詳細、深刻度集計、カバレッジ、
前回比較、JSON/HTMLレポートの取得。

運用：
ヘルスチェック、バージョン情報、統一エラー形式、
request_idを使った追跡。

診断受付は202とジョブIDを返し、
画面はポーリングで進捗を取得してください。
入力検証、ページネーション、CORS、レート制限、
Idempotency-Keyの動作と保存期間を定義します。

【データ設計】

少なくともTarget、VerificationChallenge、
CriticalityAssessment、ScanJob、Finding、
CvssAssessment、Report、OutboxEvent、AuditEventを扱います。

DynamoDBのアクセスパターン、キー、インデックス、
所有者による分離、条件付き更新、TTL、
削除・保存期間を明示してください。
検索のための全件Scanに依存しない構成にします。

CVSS未評価はnull等で明示し、0.0へ置換しません。
診断開始時の重要度設定・ルールバージョンを保存し、
後日の設定変更で過去の結果を黙って変更しないでください。

【ジョブの整合性・復旧】

状態遷移を定義してください。
例：
QUEUED → RUNNING → SUCCEEDED / FAILED
QUEUED / RUNNING → CANCEL_REQUESTED → CANCELLED

タイムアウト、配送失敗、DLQ移行時の状態も説明してください。

ジョブ登録とSQS送信の二重書き込みに対し、
DynamoDBトランザクションを用いたOutbox方式を基本とします。
ジョブと配送イベントを同時記録し、配送LambdaからSQSへ送ります。

配送後の記録失敗による重複を想定し、
配送と実行の両方を冪等にしてください。
未配送イベントの再送と、滞留ジョブの復旧処理を用意します。

SQSは少なくとも1回の配送を前提とし、
条件付き更新、実行リース、試行回数等により
同じジョブの同時実行と結果の上書きを防いでください。
期限切れの旧ワーカーが結果を確定できない設計にします。

Visibility Timeout、Lambda Timeout、
リトライ、DLQ、バッチサイズを整合させてください。
複数メッセージを扱う場合は部分失敗応答を実装します。

キャンセルは協調的に実装し、
通信・ページ処理の区切りで状態を確認してください。
すでに送信済みのHTTP要求まで即時停止できるとは表示しません。

利用者別の上限、対象ホスト別の実行制御、
全体の同時実行数をBEで強制してください。
別ユーザーから同じ対象への実行でも負荷制限が働くようにします。

────────────────────
4. LocalStack・安全性・運用要件
────────────────────

【LocalStackでの実行】

Docker ComposeとLocalStackを使って、
画面→API Gateway→API Lambda→Outbox配送→SQS→診断Lambda
→DynamoDB/S3→画面の結果取得、までを動作させてください。

ローカルのUvicorn起動だけを、
Lambda連携の検証完了として扱わないでください。
高速開発用のUvicornモードは追加して構いませんが、
統合検証モードとコマンドを分けます。

実装開始時に、固定するLocalStack版、イメージ、
必要なプランと認証トークン、
API Gateway、Lambda、SQS、DynamoDB Streams、
S3、認証関連機能の対応状況を公式資料で確認します。

対応するサービス名だけでなく、
利用するAPI、イベント連携、実行環境まで確認してください。
未対応・未検証の機能は対応表に記載します。

認証に代替が必要な場合は、
ローカル限定のOIDCプロバイダ等を使用し、
本番と同様に署名付きトークンを検証してください。
単純に認証・認可を無効化する方法は禁止します。

CloudFront、Cognito、IAM等の本番との差分を記録し、
ローカルで未検証の挙動はAWS移行前の検証項目にします。

ホスト、Composeコンテナ、Lambda実行コンテナの
通信経路と接続先を区別してください。
コンテナ内でlocalhostが別の場所を指す問題を考慮します。

LocalStack用の認証トークンをGitやログに保存しません。
通常のローカル起動・テスト・デプロイが、
実AWSへ誤接続しないガードを設けてください。

事前条件を満たした環境で、
make bootstrap、make local-up、make local-deploy、
make test、make local-down等により再現可能にしてください。
実際のコマンド名と必要な準備はREADMEに記載します。

【診断対象のテスト環境】

安全な設定と問題のある設定を切り替えられる
制御下のテストサイト、DNS、TLSテスト環境を用意します。

通常の本番ポリシーはプライベートIPへの診断を拒否します。
ローカル統合テストでは、固定したテスト対象だけを許可する
専用のネットワークポリシーを注入してください。

任意のプライベートIPを許可する汎用スイッチは設けません。
診断対象からLocalStack、認証基盤、Docker、
ホスト環境へ横移動できないように分離してください。

テスト専用設定・資格情報・接続許可が
本番成果物や本番設定に混入しないことをCIで検証します。

【SSRF・通信制御】

入力URLはHTTP/HTTPSのみ、初期版のポートは80/443のみ許可します。
ユーザー情報を含むURL、不正なホスト表記等を正規化・検証します。

localhost、プライベート、リンクローカル、
予約済み等の非公開アドレス、メタデータエンドポイントへの
接続を拒否してください。
IPv4、IPv6、IPv4 mapped IPv6等を考慮します。

DNSの全回答と各リダイレクト先を検証し、
名前解決後に未検証のIPへ再解決・接続しないでください。
実際の接続先IPを制約しつつ、
TLSのSNI、証明書検証、Hostヘッダーを正しく扱います。

所有確認のためのHTTP取得にも同じ対策を適用してください。
HTTPクライアントの環境変数由来のプロキシ利用も明示的に制御します。

アプリのSSRF対策に加え、
AWS上の送信経路と多層防御の方針を説明してください。
Security Groupだけでドメイン単位の制御ができるとは扱いません。
VPCやNAT等を採用する場合は費用と通信経路を明示します。

サイトの負荷を抑えるため、
ホストごとの並列数、待機間隔、ページ数、
リダイレクト回数、通信タイムアウト、
圧縮展開後の取得サイズ、総実行時間に上限を設定します。
初期値と根拠を設定ファイル・設計書に記載してください。

【結果の安全な取り扱い】

取得したHTMLを信頼せず、画面でそのまま実行しません。
HTMLレポートでも証拠をエスケープしてください。

Cookie値、認証トークン、秘密情報、
個人情報をログ・所見・監査記録に保存しないでください。
生のレスポンス保存を標準にせず、必要最小限の証拠を秘匿化します。

S3は非公開とし、取得時にも認可を実施します。
署名付きURLを使う場合は短い有効期限とし、
URL自体をログへ残さないでください。

対象削除時は進行中ジョブを制御し、
削除後にワーカーが結果を再作成しない設計にしてください。
ユーザーデータと監査記録の保持方針を分けて定義します。

【運用・費用】

IAM最小権限、暗号化、ログ保持、
監査、アラーム、DLQ対応、復旧手順を用意します。

構造化ログにrequest_id、job_id、処理時間、
成功・失敗・再試行を記録し、機微情報は含めません。
対象サイトの応答内容や完全なURLを無条件にログ出力しません。

Lambdaエラー、キュー滞留、DLQ件数、
長時間RUNNINGのジョブ、配送失敗を監視します。

月間利用者数、診断件数、ページ数、
保存期間、ログ量を仮定して概算費用を示してください。
LocalStackの利用費用とAWS費用を分け、
料金の確認日と参照元を記載します。

5. 開発手順・検証・納品条件
────────────────────

【進め方】

最初に既存リポジトリと適用される指示を確認してください。
既存ファイルや利用者の変更を無断で破壊しません。

まず要件整理、構成図、依存図、
画面一覧、データモデル、API仕様、
重要度の決定表、CVSS方針、優先度の決定表、
LocalStack対応表、実装順序を提示してください。

重大な不明点だけを質問し、
通常の実装判断は仮定と理由を記録して進めてください。
実装方針の提示だけで終了せず、動作するMVPまで進めます。

実装は、対象登録から診断結果表示までの縦の経路を先に完成させ、
その後に評価、再診断、復旧、運用機能を加えてください。

本番AWSへのデプロイ、実サイトへの診断、
費用が発生する外部サービスの契約は、
明示的な指示があるまで実行しないでください。
自動テストは制御下のテストサイトを対象にします。

【テスト】

Domain・Application：
診断判定、重要度分類、優先度、状態遷移、
認可、キャンセル、CVSS未評価の扱いを、
AWSや外部ネットワークなしで検証します。

Adapter・統合：
LocalStack上で永続化、Outbox配送、SQS実行、
レポート保存、認証・認可を検証します。

異常・セキュリティ：
SSRF、DNSリバインディング、リダイレクト、
他ユーザーのID指定、表示時のXSS、
重複配送、配送途中の障害、実行リース切れ、
キャンセル競合、削除競合、DLQ、復旧を検証します。

FE・契約：
主要画面の操作、エラー表示、深刻度と重要度の区別、
未評価表示、OpenAPIからの生成物の整合性、
LocalStack接続によるE2Eを検証します。

アーキテクチャ・CI：
禁止依存、型、Lint、ビルド、テスト、
IaC synth、シークレット検出、依存関係監査、
本番へのテスト設定混入を検証します。

CVSSの計算は公式の既知ベクトルで検証し、
脆弱性を実際に検出できないケースに、
見せかけのCVSS値を付けてテストを通さないでください。

失敗を無視する設定や、根拠のない大量のスナップショットで
検証済みと扱わないでください。

【納品物】

動作するモノレポ、Docker Compose、CDK、
ロックファイル、.env.example、起動・終了スクリプト、
テストサイト、テスト、CI設定を用意してください。

README、アーキテクチャ設計書、ADR、OpenAPI、
診断ルール一覧、評価ルール、LocalStack対応表、
脅威モデル、運用・復旧手順、AWS移行手順、
費用の前提と制約を含めてください。

各ルールの参考資料は公式仕様・一次資料を優先し、
確認日と対象バージョンを記載してください。

【受け入れ基準】

新しい環境でREADMEに従い、
ローカルのFE・BE・LocalStackを起動できます。

ログイン、対象登録、所有確認、重要度分類、
診断受付、非同期実行、結果表示、再診断まで再現できます。

画面にシステム重要度の3段階、
個別所見のCVSS深刻度または未評価理由、
対応優先度、診断範囲と未実施項目が表示されます。

問題のあるテストサイトと改善後のテストサイトで結果が変わり、
他ユーザーのデータや禁止された接続先へアクセスできません。

DB登録と配送の間で障害が起きても、
重複で結果が壊れず、復旧または明確な失敗状態へ移行します。

Domain・ApplicationがAWSやWebフレームワークに依存しないことを、
自動検証で確認できます。

最終報告では、実装済み、実行して確認済み、
未検証、既知の制約を分けてください。
実行環境や資格情報の不足で確認できなかったものを、
動作確認済みと報告しないでください。
